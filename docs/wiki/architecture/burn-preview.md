# Burn preview

The burn preview predicts depth from a test the user made on a real sheet. This article covers materials, their storage, how a project and a project file refer to a material, and the burn model built from them. See also [[projects-and-svg-import]] and [[layers-and-gcode]].

## Key Takeaways

- **Model.** `Material` is `id`, `name`, `thicknessMm` and `testResults`. A `MaterialTestResult` belongs to one machine profile, because lasers differ; `getMaterialWithTestResult` keeps at most one per profile.
- **Storage.** Dexie table `materials` (key `id`, added in database version 2). `MATERIAL_REPOSITORY` is the only access. `listMaterials` leaves out rows that are not well-formed.
- **Slice `material`.** State `{ materials }`. Actions: `MaterialsLoaded`, `MaterialSaved` (upsert by id), `MaterialTestResultSaved` (unknown material ignored). Selector `selectMaterials`.
- **Active material.** `selectActiveMaterial` finds the material of the document's `materialId`; it is undefined with no id or a missing material. `selectActiveMaterialTestResult` returns only the result of the active machine profile, so switching profile never uses another laser's result.
- **Saga `watchMaterials`.** It starts listening before it reads, so a save during a slow read still reaches storage. The read races `PANEL_SIZES_READ_TIMEOUT_MS`; a timeout or failure keeps the state. Materials saved during the read win over their stored copies. Every save stores at once; a failure logs the error and shows the fixed `TOAST_MATERIAL_SAVE_FAILED`, with no automatic retry.
- **Material presets.** Reusable settings of a material on one machine profile, in Dexie table `materialPresets` (added in database version 3), with slice `materialPreset` and saga `watchMaterialPresets`. They are separate from test results. `MaterialLibraryDrawer`, a narrow one-column `BedRegionDrawer` at the left edge of the bed region beside the Material panel, opened from `MaterialSection` (a small captioned Library button beside the presets button under the full-width material select, and that presets button with `selectActiveMaterialPresetCount` that opens it filtered to the project material), lists, edits, adds and deletes them; its `MaterialLibraryEditor` shows a list view or an edit view (Back returns to the list), owns the form draft, the material filter and the layer target, keeps a saved preset open and confirms Save, Apply and Delete in one self-clearing line under the actions (`useExpiringValue`); a row applied from the list says Applied in place of its button. Materials can be added inside the library (New material beside Add preset, in the empty state, and as the last entry of the edit view's material select) through `MaterialDialog` with `onMaterialChosen`, which keeps the project material unchanged. Deleting a machine profile deletes its presets. `useApplyPresetToLayer` applies a stored preset of the active machine to a layer as one undo step, from `PresetLayerApply` in the edit pane or from the labelled Apply button each row of the active machine gets when the library was opened for a layer. The layer drawer's `LayerPresetButtons` saves a layer as a preset, asking Update existing, Save as new or Cancel in a popover inside the drawer when `getMatchingMaterialPreset` finds one for the same material, operation and machine, and opens the library for that layer. `PresetFileActions`, two icon buttons in the drawer header (upload and download arrows, named by tooltip, with a count badge on Export), exports ticked presets and imports a file for the active machine (confirmed in a toast), keeping each preset's share of its source laser (`getImportedMaterialPresets`).
- **Project.** `ProjectDocument` and `StoredProject` hold an optional `materialId`, not a copy. `ProjectMaterialSelected` is one undo step, a repeat makes no step, and it autosaves. It is not a toolpath input: a ready toolpath stays ready and the simulation keeps its time (`PROJECT_TOOLPATH_INPUT_CHANGE_ACTION_TYPES`). Undoing it is, like every undo. A stored id that is not text reads as none.
- **Project file version 3.** Adds optional `materialId` and `material` (an embedded copy) after `layers`. Versions 1 and 2 still open, with no material; a stray `material` in them is ignored.
- **Import.** `isMaterial` checks types only. `getImportedMaterial` then copies known fields, trims and cuts the name, and clamps thickness and test settings, so a speed of 0 cannot make a test dose infinite. An empty id or name rejects the file with `TOAST_PROJECT_FILE_INVALID`. The document points at the embedded material if the two ids differ.
- **Existing id wins.** `importProjectFile` calls `addMissingMaterial` before storing the project, then reloads with `MaterialsLoaded`, keeping materials on screen whose store failed. A local material with the same id keeps its name and results.
- **Depth estimate.** `getBurnDepthBasis` turns the test result into a depth per dose (dose = power / feed); `getBurnDepthPrediction` gives depth, level (through, borderline, not through) and sureness. With no test the estimate is `GUESS_DEPTH_MM_PER_DOSE`, and no cell ever counts as through.
- **Grid.** `getBurnDoseGrid` keeps the dose per cell of the sheet (job bounds + 10 mm, at most 1,000,000 cells, at least 0.1 mm). Floods use `visitBurnGridNeighbourCells`, a callback rather than a list: a list per cell cost 15-20 % of a 100,000-move build.
- **Grid limit.** The cell grows with the sheet (about 0.4 mm on 400 mm, about 1 mm on 1000 mm), so uncut tabs smaller than a cell or two can be missed and a part held by them may show as free (measured up to 0.6 mm on 400 mm, 1.5 mm on 1000 mm).
- **Parts.** `getBurnParts` finds the regions closed cuts enclose, their status and a parent tree by `parentId`. `getBurnChainGeometryGroups` treats chains with the same points (within `CUT_SAME_GEOMETRY_TOLERANCE_MM`, any start or direction) as one groove whose doses add; `getBurnWallCellPrediction` caps a wall at borderline when it reaches through only on a sum of anything else, or when a stretch of a chain is weaker than the rest of its cell. `FREE` and `BORDERLINE` parts can lift (`isBurnPartLiftable`); a `NOT_THROUGH` part cannot.
- **Meshes.** `getBurnRegionMeshes` gives the sheet first, then one mesh per liftable part. Height 0 is the sheet bottom and the thickness its untouched top; through cells have no geometry; depths round to `BURN_DEPTH_QUANTUM_MM`; quads merge along rows. A `NOT_THROUGH` part goes to its nearest liftable ancestor, else the sheet. A remaining wall goes to the outermost mesh it touches, so an engraving rises with its part and the wall of a borderline part stays behind. A cell that is not through keeps a floor one step high, however deep its estimate. A face darkens with its depth up to `BURN_FULL_SHADE_DEPTH_MM` (0.2 mm), whatever the sheet thickness, so shallow fills and shading show as burns rather than bare outlines.
- **Triangle cap.** Over `BURN_MESH_MAX_TRIANGLES` (2,000,000) the surface doubles its cell size until it fits. A block with any through cell is empty, so cuts stay open and only look wider. Quads are counted first, then written to exact-size arrays.
- **Worker.** `BrowserBurnModelWorkerClient` mirrors the toolpath client: a cancel terminates the worker, a request id guards answers. `runBurnModelWorkerRequest` hands the mesh buffers over as transferables; an error is a fixed-shape message and its text only reaches the log.
- **Slice `burnModel`.** Status `IDLE`, `BUILDING`, `READY`, `STALE`, `FAILED`. `BurnModelReady` clears selection and lifts. `ToolpathRequested`, `ToolpathMachineAreaChanged`, `ActiveMachineProfileSelected`, every document change, and a save or test result of the built material or selecting another material make a ready model stale, whatever the view. A material change for another material, or for the same id, is ignored. Lifts have no upper limit and an absolute floor: no part goes below its place in the sheet, even inside a lifted parent. They change nothing in the project; `selectBurnPartEffectiveLiftMm` adds the lifts of all ancestors. A build stopped by one of those changes or by a view change leaves `BUILDING`.
- **Saga `watchBurnModel`.** Builds in every view whenever a material exists and the toolpath is ready, so the Cut check warning count on the muted Design and Toolpath line is current without a visit to 3D. The watcher is a take loop that also hears the toolpath input changes: these build nothing but cancel a running build. A material change is not a toolpath input, so it rebuilds directly. A view change is not watched: it neither builds nor cancels, which keeps the lifts and any running build. A failure logs and shows `TOAST_BURN_MODEL_FAILED`.
- **Selecting and staleness by material.** `BurnModelRequested` carries the material id, kept as `builtMaterialId`. Only a save or test result of that material, or selecting a different one, makes the model stale. `watchBurnModel` is a take loop instead of `takeLatest`, because an ignored action must not cancel a running build: a save or result of another material, the same material selected again, and `MaterialsLoaded` while the model is ready or building. `MaterialsLoaded` otherwise builds, so materials read after 3D opened still give a model.
- **Scene and lazy chunk.** `BurnPreviewPane` loads `burn.scene.runtime` with three.js in a lazy chunk. A failed load or no WebGL shows the fixed `BURN_PREVIEW_NO_WEBGL`, and everything outside the scene keeps working.
- **Legend.** While a model is shown, `BurnPreviewPane` draws `BurnShadingLegend` at the bottom left of the scene: a pill with "Clean" and "Burnt" around a gradient bar fed by `BURN_SCENE_CLEAN_COLOUR` and `BURN_SCENE_BURNT_COLOUR` through custom properties, one `role="img"` with a sentence for screen readers.
- **Empty state.** `selectBurnPreviewEmptyState` says why there is no current model: `OUT_OF_DATE` (model stale or toolpath not ready and not being generated), `FAILED` or `BUILDING` (also while the toolpath is generated, so the first visit shows the shimmering cube plate rather than a warning); undefined for a ready model. The pane and the Cut check both word it, so neither shows old parts as current. A missing material no longer blocks the model: `runBurnModelAction` builds with `NEUTRAL_PREVIEW_MATERIAL` (`src/utils/materials/neutral.preview.material.ts`), and `MaterialsLoaded` rebuilds a model whose built material is not the project's. The pane shows a non-blocking material chip (`BurnPreviewStateMessage`) while no material is active.
- **Cut check.** `CutCheckPanel` sits in `DesignPanel` in 3D, where Objects is hidden. It starts folded (`isExpanded` false): the heading carries a cut-risk count `Tag` (one per warning group, hidden at zero, a scissors icon and a tooltip named by `CUT_CHECK_WARNING_COUNT`, "2 cut risks (do not lock Start)", so it never reads as the toolpath warning count) and an Up/Down `IconActionButton` with `aria-expanded`; a part selected in the scene opens it. Open, it has the counts, warnings grouped by `getCutCheckWarningGroups` (kind, layer, shown depths, certainty), each group one compact `CutCheckWarningRow` (warning icon, layer name, "predicted / needed mm", and a Fix button that dispatches `LayerSettingsOpenChanged` so the layer settings drawer opens on that layer; the sentence from `getCutCheckWarningText` is the row's tooltip and accessible name), an Estimate or Guess tag in the summary whose tooltip carries the note (and, for a guess, the pointer to the test sample), a list with one row per part (the only way to select a not-through part, which has no mesh) that is cut down to the selected row above `PART_LIST_FULL_ROW_LIMIT` parts, and the estimate or guess note; there is no inner scroller. Rows and scene share `hoveredPartId`; a selected row scrolls only the nearest scrolling panel, with a margin (`getCutCheckListScrollTopPx`); stacked, that panel does not scroll, so the scene stays in view. Warnings never block export.
- **Toolbar and first material.** By the user's decision the material is chosen in Design: `ProjectMaterialSelect` in the Material panel of `DesignPanel` selects it and opens `MaterialDialog`, which starts with an empty name, keeps Save off until `getMaterialFieldErrors` passes (the name error and save note wait until the name field loses focus), offers the match from `getMatchingMaterial` without blocking, then dispatches `MaterialSaved` and `ProjectMaterialSelected`. An existing material cannot be edited yet. `BurnPreviewToolbar` in the 3D header shows the material as read-only text; Enter test result opens `TestSampleDialog`.
- **Lifting.** The selected liftable part shows an orange arrow (`BurnPartLiftControl`, `add.burn.lift.drag.listener.ts`) to drag; the control is a bar docked below the scene, in normal flow, with a click hint before selection, the live height and `BurnPartLiftsReset` (Put all back); arrow keys on it step `BURN_PART_LIFT_STEP_MM` (1). `add.burn.scene.hover.listener.ts` reads the part under a mouse at most every `BURN_SCENE_HOVER_MIN_INTERVAL_MS`, and `hoverBurnPart` draws only on a change. The selected part gets an orange ink line. Orbit stops at `BURN_SCENE_MAX_POLAR_ANGLE_RADIANS` (80 degrees); `fitBurnSceneView` and `showBurnSceneFromTop` back the Fit and Top buttons; `getBurnSceneFitZoom` sizes the sheet to the canvas, and a resize fits again until the user moves the view. Materials draw both sides because T-junctions in flat faces let single pixels through; drawing the back shows wood there instead of dark speckle. There is no slider and no upper limit; height 0 is absolute (`selectBurnPartEffectiveLiftMm`). Pieces are cel-shaded with an ink outline drawn only where a wall meets the sheet face. The camera is orthographic only.
- **Test sample (user's decision: it moved to Design, and its own export is gone).** `AddTestSampleButton` in the Layers panel (Design view, once the bed has objects; on an empty bed only the bed card offers it) dispatches `SampleJobAddRequested`; `addSampleJob`, in the project command queue, adds `getSampleJobObject` (a 50 mm Line square plus a black-to-white gradient, 5 mm in from the origin corner) with `ProjectObjectsAdded`, so one undo step. `getSampleJobLayers` derives layers by colour: existing layers stay untouched, new ones are forced on as Line (square) and Fill (gradient). It burns through the usual layers, toolpath and G-code export. `TestSampleDialog`, opened by Enter test result in 3D, holds only the result: no outcome at the start, optional depth (`getTestDepthErrorKey`), and power, speed and passes prefilled by `getSampleCutSettings` (the sample is recognised by its exact SVG text; else the first Line layer) and range-checked. It dispatches `MaterialTestResultSaved` for the active profile. Shading comes from the gradient in the design; the app has no shading control.
- **SVG drop in 3D.** There is no bed, so `useSvgFileDrop(false)` refuses the drag and imports nothing, while still stopping the browser from opening the file.
