# Running jobs

Roadmap item 5, slices 1 (Start job), 2 (progress, Pause and Resume) and 3 (Frame job). Simulator-tested only: not production-ready until the laser checks are done. For slice 3 the ACMER checks are still pending: the dot visible at about 0.05 W including at corners, dark while paused, and dark when the head stops. Not built yet: slices 4 to 6 (overrides, pre-flight, long jobs). User steps: `docs/howto/running-jobs.md`. Slices: `docs/superpowers/specs/2026-11-03_(03)_running-jobs.spec.md`; Frame job: `docs/superpowers/specs/2026-11-04_(02)_frame-job.spec.md`.

## Key Takeaways

- **Start conditions.** `selectJobStartBlockedReasonKey` is shared by `JobCard` and `runGrblJob`, so the saga does not rely on a disabled button. Toolpath warnings block a start, and so does any active content off the bed: `selectToolpathBedOverrun` runs `getToolpathBedOverrun` over the toolpath moves (the same end points that become the G-code X and Y words; the origin corner only mirrors them inside the bed), with a tolerance of half the last G-code decimal, so a Start that is allowed never sends the head past the bed. Skipped and hidden content is not in the toolpath, so it never blocks. Frame maps that reason to `FRAME_START_BLOCKED_OFF_BED`. `selectJobStartBlockedReasonKeys` lists every current reason; the Start lock dot (`ActionLockNote`, always in `--color-warning`, never the hover colour) opens a popover above the button, clear of its caption, listing each reason with a warning icon.
- **End of a job.** The last `ok` means buffered, not burned. The run stays `finishing` until the next Idle report. A stop, reset, alarm or controller reset gives `interrupted`, because a reset also leaves the machine Idle. The saga watches for a stop or reset from the start of the run, not only during that wait, because the last lines can still be answered while a stop waits for the machine to come to rest. After a stop request a run never ends `completed`, even if an Idle report arrives before the stop has finished.
- **Stop keeps the locks.** After a stop request the run stays active until `MachineStopFinished`, which `runGrblMachineStop` puts when the stop sequence ends, also if the program ended earlier or an Alarm report came during the stop. A stalled port never lets that action come, so the run ends `interrupted` at the latest `GRBL_STOP_FINISH_MAX_WAIT_MS` (5000 ms) after the request. A line typed earlier would be wiped by the reset. Reset and controller reset end the run at once, as that action never comes for them.
- **Progress.** `GrblProgramStreamer` emits `PROGRAM_PROGRESS` when a real run starts and for each answered line, not during a check. Answered lines run slightly ahead of the burn, as GRBL buffers them, so `JobRunProgress` keeps the bar neutral at 100% instead of showing the antd success mark.
- **Pause.** `selectJobPauseControl` decides between pause, resume and their blocked forms, and `runGrblJobPauseCommand` repeats that check. Resume is offered at `Hold:0` and `Door:0`, the states where GRBL accepts it. `JobCard` shows Paused while one of `JOB_PAUSED_CONTROLS` is offered. Pause is refused unless `$32` reads `1`, because without laser mode the beam can stay on during a hold. Known gap: `grblSettings` is only read in the handshake, so a `$32=0` typed in the console after connecting is not seen until the next connect.
- **Stale `$32`.** Settings are read at connect only, so a console line writing `$32=` or `$RST=` sets `isLaserModeUnconfirmed`, which blocks Pause until the next `ConnectionEstablished`. Other consumers of `selectGrblSettings` still see the old values.
- **Connection end.** The reducer marks an active run `interrupted`, because the saga is cancelled with the connection.
- **Air assist.** A job that ended early ended in a reset, and a finished program may end with `M9`, so `runGrblJob` then puts `MachineAirAssistChanged` off. During a run the switch does not follow the `M8` and `M9` of the program.
- **Confirmation.** The Start job `Popconfirm` registers in the overlay registry, because it is in the main view: Escape only closes it, without also stopping the machine. It closes when the start gets blocked.
- **Same program as the export.** `getProjectGcodeText` writes the G-code for both.
- **Locks.** During a run, `submitGrblConsoleCommand` and `submitGrblMachineLine` drop lines, `getMoveAvailability` and `getCanFireLaserPointer` refuse, and the air switch is off. `LeavePageGuard` also warns.
- **Frame job.** A dry run of the job: a low-power dot traces a rectangle around the whole job, then an optional grid inside it, then the head returns to where it started. It answers whether the job stays within the laser's limits, whether the head can travel the path, and (by the spot size) whether the sheet is flat.
- **Frame program.** `getFrameProgramLines` writes `M4 S<value>`, the outline with `G1` at the profile's frame speed (`feedMmPerMin`, written as `F` on the first side), the grid lines (`G0` to a line start, `G1` along it, ordered so each starts at the end nearest the last), `M5 S0`, then `G0` to the start position and a `G4 P0` dwell (the `G0` does not wait for the planner, so without the dwell the run could read Idle before the head starts back). An interrupted frame puts `MachineAirAssistChanged` off, as an interrupted job does. It is streamed through `streamProgram` by `runGrblFrame`, which reuses `followJobProgram` and `waitForJobInterruption` of `runGrblJob`, so progress, locks, STOP, Pause and Resume and the end at the next Idle report work as for a job. The `jobRun` slice has a kind (`JOB_RUN_KIND`, job or frame) so the card says Framing. A frame sends no `M8`.
- **Rectangle.** `getFrameRectangle` takes the extent of the `burn` moves of the ready toolpath, fill overscan at power 0 included, because the head really travels there; travel moves are left out, so `toolpath.bounds` is not used. The profile's margin (`frameMarginMm`, mm, 0 or more, 0 default) grows it on all four sides. Grid cell (`frameGridCellMm`: none, 10, 20 or 50 mm), margin and speed are saved per machine profile; the grid lines start from the lower left corner of the rectangle.
- **Speed.** The user asked for the trace speed to be adjustable. `frameFeedMmPerMin` is an optional profile field (like `frameMarginMm`; old profiles load), default `DEFAULT_FRAME_FEED_MM_PER_MIN` (6000 mm/min), valid from `MACHINE_JOG_FEED_RATE_MIN` to `MACHINE_JOG_FEED_RATE_MAX` (100..10000, the jog speed limits; `getMachineProfileErrors` gives `MACHINE_PROFILE_ERROR_FRAME_FEED_RATE_INVALID`). `selectFrameFeedMmPerMin` returns the default when the stored value is missing or out of range (for example from an imported file), so such a value never reaches the machine. The saga (`getFrameProgramLines`), the shown frame time (`getFrameDurationSeconds`) and the `FrameNumberInput` in the card all take that one selected value. GRBL silently caps every move at the machine's `$110` and `$111`, so the shown frame time is a lower bound: a machine slower than the chosen speed takes longer. With `M4`, a faster trace may change how visible the dot is (unverified on hardware).
- **Dot power.** `getFrameSValue` turns `FRAME_DOT_WATTS` (0.05 W) into an S value from the profile's `maxPowerWatts` and the S max the laser reports in `$30` (else the profile's), through `getValidGcodeSValueMax(getPointerSValueMax(...))` as jobs do; the pointer calls `getPointerSValueMax` alone. The S value is at least 1. `maxPowerWatts` defaults to 10 W, so a profile left at the default gets the wrong dot on a stronger laser: the card shows it as **Guide light** with the watts, and its tooltip says the dot never burns and names the profile it assumes.
- **Start conditions.** `selectFrameStartBlockedReasonKey`: those of Start job, then laser mode confirmed on (`selectIsLaserModeConfirmedOn`, shared with Pause), at least one burn move, no bed overrun, and a known work position. Frame job asks for no confirmation. A frame that would leave the bed never starts: `getFrameBedOverrun` names the edge and the distance and the card shows them.
- **Work zero model.** Work zero counts as the origin of the bed: after Set zero at machine -100,-100, machine -50,-50 reads as work 50,50. The app does not model machine travel, so the bed check is only a first filter; the machine is the authority on its limits.
- **The limit catch.** Without soft limits (`$20=1` and a homed machine) or hard limit switches, GRBL reports nothing when the head reaches the end of its travel, so the frame carries on and the head may stall. The app cannot detect that: the user watches the head. When GRBL does raise an alarm during the frame, the run ends as interrupted (`FrameRunAlarmed`) and the card says the machine reported an alarm, possibly a limit. An alarm raised by the time limit of a user's reset is not told as a limit.
- **Dot on firmware.** Motion uses `M4` with `G1`, not `$J=`, because jog lines cannot carry the laser. Stock GRBL keeps `M3` lit at a standstill, so `M3` would leave a lit dot when the head stops or pauses; `M4` (with `$32=1`) goes dark when motion stops, but the dot dims at corners and may be too faint at 0.05 W. The user chose `M4` after the review found this; the ACMER check is pending.
