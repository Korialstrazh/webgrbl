# Machine control

Machine profiles hold the facts that differ from laser to laser, so the app can drive any GRBL laser: bed size, rated power, `$30` S max, origin corner, homing switches, air assist and jog speed. The active profile sizes the bed and scales the laser pointer's power. The machine commands (jog, home, work zero, air, pointer) are built as G-code lines by pure builders and sent through one line action; the low-power laser pointer is a hold-to-fire saga with safety cut-offs. The Move card, the Laser pointer card and the Machine profiles dialog put all of it in front of the user. Developer walkthrough: `docs/howto/machine-control.md`.

## Key Takeaways

- **Model.** `MachineProfile` (`id`, `name`, `maxPowerWatts`, `workAreaXMm`, `workAreaYMm`, `sValueMax`, `originCorner`, `hasAirAssist`, `hasHomingSwitches`, `jogFeedRate`). `newMachineProfile(overrides)` fills the defaults ("My laser", 400 x 400 mm, 10 W, S max 1000, front-left, no air assist, no homing, jog 1500 mm/min) and a new `crypto.randomUUID()` id.
- **Validation.** `getMachineProfileErrors(profile)` returns one `{field, messageKey, messageParameters?}` per invalid field: name required, 0 < watts <= 500, 0 < work area <= 5000 mm (`BED_MAX_TRAVEL_MM`), S max an integer 1..100000, jog feed 100..10000 mm/min. Bounds live in `machine.profile.constants.ts` and are interpolated into the messages.
- **Storage.** `MACHINE_PROFILES_STORAGE` keeps `{ version: 1, activeProfileId, profiles }` in `localStorage` under `webgrbl.machineProfiles`. Reads go through type guards; corrupt, missing or blocked storage reads as an empty document; profiles failing range validation are dropped and a dangling `activeProfileId` is cleared. Writes swallow storage errors.
- **Import and export.** `getMergedProfilesDocument(current, imported)` validates the import and appends its profiles, giving clashing ids a new id; `undefined` means invalid input. `getProfilesExportText` writes the document as indented JSON.
- **Slice `machineProfile`.** State is the stored document. Actions: `MachineProfilesLoaded`, `MachineProfileSaved` (upsert by id), `MachineProfileDeleted` (deleting the active profile clears `activeProfileId`), `ActiveMachineProfileSelected` (an unknown id is ignored), `MachineProfilesImported` (takes over the merged document), `MachineProfileReadFromLaserRequested`, `MachineProfileUpdateFromLaserAccepted`. Selectors: `selectMachineProfilesDocument`, `selectMachineProfiles`, `selectMachineProfile(id)`, `selectActiveMachineProfile`.
- **Reading a laser.** `getProfileValuesFromSettings(settings)` maps `$130` -> X, `$131` -> Y, `$30` -> S max, `$22 === '1'` -> homing and `$32 === '1'` -> laser mode. Values are checked by building a candidate profile and running the profile validation, so the ranges have one owner; an invalid value falls back to the default. `getValidlyReportedProfileValues(settings)` returns only the values the laser reports validly (missing or out-of-range ones are left out); `getProfileValuesFromSettings` fills the gaps with defaults on top of it. The sagas use only the validly reported values, so a default is never taken for a reading. Setting numbers are `GRBL_SETTING_*` in `grbl.constants.ts` (X/Y travel in `bed.constants.ts`).
- **Saga `watchMachineProfiles`.** At start it loads the stored document (`call` on `MACHINE_PROFILES_STORAGE`) and puts `MachineProfilesLoaded`; after every saved, deleted, selected or imported change it stores the document again.
- **On connect** (`ConnectionEstablished`), only when `$130` and `$131` are both validly reported: with no profiles at all, it creates "My laser" from the reported values, makes it active and shows the info toast `TOAST_PROFILE_CREATED` (profiles without an active one create nothing); with an active profile whose work area differs, it shows the warning toast `TOAST_PROFILE_DIFFERS` (both sizes) and changes nothing; the toast points the user to the Machine profiles dialog. Without a valid work area no profile is created and the bed keeps its size-unknown placeholder. When `$32` is reported and not `1` it shows the warning `TOAST_LASER_MODE_OFF`.
- **Update from the laser.** `MachineProfileUpdateFromLaserAccepted` and `MachineProfileReadFromLaserRequested` apply the validly reported work area, S max and homing to that profile, keeping the profile's own value for anything not validly reported, and save it (which persists it). They do nothing while disconnected, since empty settings would reset the profile to defaults, or for an unknown id. The read also repeats the laser-mode warning.
- **Bed.** `BedPanel` passes `selectActiveMachineProfile` to `getBedDimensions`; a valid profile work area wins over `$130`/`$131` and shows no placeholder, connected or not (see [[app-shell]]).
- **Command builders.** Pure functions in `src/utils/machine/` return G-code lines; nothing there touches the store. Fixed lines are `MACHINE_COMMAND` (`$H` home, `G10 L20 P1 X0 Y0` set work zero, `M5` pointer off, `M8` / `M9` air on / off). `getJogCommand(direction, stepMm, feedRate)` gives `$J=G91 G21` plus the X / Y words of the direction (`JOG_DIRECTION` n, ne, e, se, s, sw, w, nw; north is +Y, east is +X; a zero sign leaves the axis out) and `F`. `getGoToWorkZeroCommand(feedRate)` gives `$J=G90 G21 X0 Y0 F...`. `getFormattedGcodeNumber` rounds to 3 decimals and never prints `-0`. Jog step sizes are 0.1 / 1 / 10 / 50 mm (default 10).
- **Sending a line.** `MachineLineRequested {line}` (in `machine.status.state.ts`) makes the controller saga send the line as-is, without adding it to the console command history; it is only handled while connected, so a line requested while disconnected is dropped.
- **Pointer power.** `getPointerOnCommands(percent, sValueMax)` gives `M3 S<n>` and `G1 F100`, with `n = round(sValueMax * percent / 100)` and at least 1. The percent is clamped to 0.1..5 by `getClampedPointerPowerPercent`, the one owner of the pointer range, used by the builder and by the slice; so the pointer can never fire above 5 % of S max. `getPointerSValueMax(laserSettings, activeProfile)` picks that S max: the `$30` the connected laser reports validly (through `getValidlyReportedProfileValues`), else the active profile's `sValueMax`, else `DEFAULT_MACHINE_S_VALUE_MAX`. The laser's own `$30` wins, so a profile S max above the laser's (a 1000 profile on a `$30=255` laser) cannot lift the pointer past 5 % of `$30`.
- **Slice `laserPointer`.** State `isFiring` and `powerPercent` (default 1). Actions: `LaserPointerPowerChanged {percent}` (clamped), `LaserPointerFireRequested`, `LaserPointerReleaseRequested` (both from the UI), `LaserPointerFiringStarted`, `LaserPointerFiringStopped` (both from the saga only). Selectors: `selectIsLaserPointerFiring`, `selectLaserPointerPowerPercent`.
- **Saga `watchLaserPointer` (pointer safety).** On a fire request, only when connected and the last status is `Idle`, it puts `MachineLineRequested` for each pointer-on line, scaled by `getPointerSValueMax` over the connected laser's settings (`selectGrblSettings`) and the active profile, then `LaserPointerFiringStarted`. It then races every cut-off and stops on the first: release; window `blur`; document `visibilitychange` to `hidden` (one event channel, closed afterwards); `ConnectionStatusChanged` to anything but connected (disconnect or connection lost); `MachineStopRequested`; a `MachineStatusReceived` in `Alarm`; and the 10 000 ms maximum hold (`MAX_POINTER_HOLD_MS`). Stopping puts `M5` only when the connection status at that moment is still connected (a line could not be sent otherwise), then `LaserPointerFiringStopped`; the stop runs in a `finally`, so an error also turns the pointer off. Fire requests that arrive while firing are not taken and are ignored. Event names live in `browser.events.constants.ts`.
- **Move card.** `MoveCard` (in `MachinePanel`) builds a line with the pure builders and dispatches `MachineLineRequested`; it never touches the controller. `getMoveAvailability({ isConnected, machineState, hasHomingSwitches, isPointerFiring })` (`MoveAvailabilityConditions`) gates the controls: jog and go-to-zero need connected and `Idle` or `Jog`, Home needs homing switches and `Idle` or `Alarm`, Set zero needs `Idle`; all of them are locked while the pointer fires (`selectIsLaserPointerFiring`), since a move with `M3` active would drag the beam along its path (a second finger could reach the pad during a hold). The 3 x 3 pad (`JOG_PAD_CELLS`: eight arrow buttons around an Origin centre that sends the go-to-work-zero line), an antd `Segmented` for the step (default 10 mm, kept in component state) and `JogSpeedInput` (an antd `InputNumber`, kept as a draft and saved on blur or Enter through `MachineProfileSaved` with the clamped feed rate; disabled without an active profile). Home runs `$H` and is rendered only when the active profile has homing switches; Set zero sends `G10 L20 P1 X0 Y0`, an EEPROM offset that Stop and reset keep. Unlock and Reset stay in the Status card (see [[app-shell]]).
- **Laser pointer card.** `LaserCard` holds the power `Slider` (0.1..5 %, step `POINTER_POWER_STEP_PERCENT`, dispatching `LaserPointerPowerChanged`) with the approximate watts of the active profile (`getPointerApproximateWatts`), `PointerFireButton`, the firmware note, the Frame job button (still `ComingSoon`) and, only for a profile with air assist, an antd `Switch` that puts `MachineAirAssistChanged {isAirAssistOn}` and sends `M8` / `M9`. The switch reads `selectIsAirAssistOn` from the `machineStatus` slice, which starts as off and turns off again on `MachineStopRequested` and `MachineResetRequested` (both end in a soft reset, which switches the coolant off) and when the connection ends or is lost (the laser's air state is unknown afterwards).
- **Fire button.** `PointerFireButton` is enabled by `getCanFireLaserPointer(isConnected, machineState)` (connected and `Idle`, shared with the saga's own check), and stays enabled while the pointer fires even if the state leaves `Idle`, because a disabled button may never receive the `pointerup` / `pointerleave` that release it. It requests fire on a primary-button `pointerdown` (not on other buttons) and on a non-repeating Space or Enter `keydown`, and requests release on `pointerup`, `pointerleave`, `pointercancel`, `blur`, the key `keyup` and on unmount. Release is idempotent, so the extra triggers are harmless; the saga holds the cut-offs that do not depend on the UI.
- **Machine profiles dialog.** `TopBar` opens `MachineProfilesDialog` (a `BedRegionModal`) with its "Machine profiles" button. `MachineProfilesEditor` keeps the edited profile in state (the active one, else the first, else a new one): `ProfileList` (antd `Menu` with an Active tag, New profile, Set active, Delete with a `Popconfirm`), `ProfileFileActions` (Import reads a file through a hidden file input and merges it with `getImportedProfilesDocument`, an invalid file shows `TOAST_PROFILE_IMPORT_INVALID`; Export downloads `getProfilesExportText`; GRBL settings is `ComingSoon`) and `ProfileForm` (one field per profile value, errors from `getMachineProfileErrors`, Save, and "Read from connected laser" through `LaserReadingAlerts`, which lists the values the laser reported, warns when none were and shows `MACHINE_PROFILES_LASER_MODE_OFF` when `$32` is reported off; reading fills the form only and Save keeps it).
- **Connection pill.** `ConnectionPill` shows the active profile's name.
- **Hardware.** Stock GRBL in laser mode (`$32=1`) keeps the laser off without motion, so a stationary pointer (`M3` with `G1 F100`, no motion) lights there only with `$32=0`; many diode-laser firmwares, including vendor builds like the ACMER's, light it anyway. Whether it lights on the ACMER is pending the hardware check. The card's firmware note `MACHINE_LASER_FIRMWARE_NOTE` says "Some firmwares keep the laser off while the head stands still" and lists the cut-offs, with the hold limit interpolated as `MAX_POINTER_HOLD_MS / MILLISECONDS_PER_SECOND` seconds. The laser-mode warnings (`TOAST_LASER_MODE_OFF`, and `MACHINE_PROFILES_LASER_MODE_OFF` in the dialog) speak only about burn spots, never about the pointer.
- **Tests.** Saga tests run `newStore` against a `SimulatedLaserTransport` over a shared `GrblSimulator` whose settings are changed before connecting, with fake timers. The pointer saga tests read the requested lines by spying on `Action.prototype.toPlainObject`, which every class action (saga puts included) passes through on its way into the store. `vitest.setup.ts` clears the jsdom `localStorage` after every test.
