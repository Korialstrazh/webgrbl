# Machine control

Machine profiles hold the facts that differ from laser to laser, so the app can drive any GRBL laser: bed size, rated power, `$30` S max, origin corner, homing switches, air assist and jog speed, and the laser pointer power (`pointerPowerPercent`, optional: a profile saved before it existed has none and uses the session's power). The active profile sizes the bed and scales the laser pointer's power. The machine commands (jog, home, work zero, air, pointer) are built as G-code lines by pure builders and sent through one line action; the low-power laser pointer is a hold-to-fire saga with safety cut-offs. The Move card, the laser pointer row of the Job card and the Machine profiles dialog put all of it in front of the user. Developer walkthrough: `docs/howto/machine-control.md`.

## Key Takeaways

- **Model.** `MachineProfile` (`id`, `name`, `maxPowerWatts`, `workAreaXMm`, `workAreaYMm`, `sValueMax`, `originCorner`, `hasAirAssist`, `hasHomingSwitches`, `jogFeedRate`). `newMachineProfile(overrides)` fills the defaults ("My laser", 400 x 400 mm, 10 W, S max 1000, front-left, no air assist, no homing, jog 1500 mm/min) and a new `crypto.randomUUID()` id.
- **Validation.** `getMachineProfileErrors(profile)` returns one `{field, messageKey, messageParameters?}` per invalid field: name required, 0 < watts <= 500, 0 < work area <= 5000 mm (`BED_MAX_TRAVEL_MM`), S max an integer 1..100000, jog feed 100..10000 mm/min. Bounds live in `machine.profile.constants.ts` and are interpolated into the messages.
- **Storage.** `MACHINE_PROFILES_STORAGE` keeps `{ version: 1, activeProfileId, profiles }` in `localStorage` under `webgrbl.machineProfiles`. Reads go through type guards; corrupt, missing or blocked storage reads as an empty document; profiles failing range validation are dropped and a dangling `activeProfileId` is cleared. Writes swallow storage errors.
- **Import and export.** `getMergedProfilesDocument(current, imported)` validates the import and appends its profiles, giving clashing ids a new id; `undefined` means invalid input. `getProfilesExportText` writes the document as indented JSON.
- **Slice `machineProfile`.** State is the stored document. Actions: `MachineProfilesLoaded`, `MachineProfileSaved` (upsert by id), `MachineProfileDeleted` (deleting the active profile clears `activeProfileId`), `ActiveMachineProfileSelected` (an unknown id is ignored), `MachineProfilesImported` (takes over the merged document). Selectors: `selectMachineProfilesDocument`, `selectMachineProfiles`, `selectMachineProfile(id)`, `selectActiveMachineProfile`.
- **Reading a laser.** `getValidlyReportedProfileValues(settings)` maps `$130` -> X, `$131` -> Y, `$30` -> S max, `$22 === '1'` -> homing and `$32 === '1'` -> laser mode, and returns only the values the laser reports validly (missing or out-of-range ones are left out). Values are checked by building a candidate profile and running the profile validation, so the ranges have one owner. The sagas and the dialog use only the validly reported values, so a default is never taken for a reading; `getReportedProfileFields` turns them into profile fields. Setting numbers are `GRBL_SETTING_*` in `grbl.constants.ts` (X/Y travel in `bed.constants.ts`).
- **Saga `watchMachineProfiles`.** At start it loads the stored document (`call` on `MACHINE_PROFILES_STORAGE`) and puts `MachineProfilesLoaded`; after every saved, deleted, selected or imported change it stores the document again.
- **On connect** (`ConnectionEstablished`), only when `$130` and `$131` are both validly reported: with no profiles at all, it creates "My laser" from the reported values, makes it active and shows the info toast `TOAST_PROFILE_CREATED` (profiles without an active one create nothing); with an active profile whose work area differs, it shows the warning toast `TOAST_PROFILE_DIFFERS` (both sizes) and changes nothing; the toast points the user to the Machine profiles dialog. Without a valid work area no profile is created and the bed keeps its size-unknown placeholder. When `$32` is reported and not `1` it shows the warning `TOAST_LASER_MODE_OFF`.
- **Bed.** `BedPanel` passes `selectActiveMachineProfile` to `getBedDimensions`; a valid profile work area wins over `$130`/`$131` and shows no placeholder, connected or not (see [[app-shell]]).
- **Command builders.** Pure functions in `src/utils/machine/` return G-code lines; nothing there touches the store. Fixed lines are `MACHINE_COMMAND` (`$H` home, `G10 L20 P1 X0 Y0` set work zero, `M5` pointer off, `M8` / `M9` air on / off). `getJogCommand(direction, stepMm, feedRate)` gives `$J=G91 G21` plus the X / Y words of the direction (`JOG_DIRECTION` n, ne, e, se, s, sw, w, nw; north is +Y, east is +X; a zero sign leaves the axis out) and `F`. `getGoToWorkZeroCommand(feedRate)` gives `$J=G90 G21 X0 Y0 F...`. `getFormattedGcodeNumber` rounds to 3 decimals and never prints `-0`. Jog step sizes are 0.1 / 1 / 10 / 50 mm (default 10).
- **Sending a line.** `MachineLineRequested {line}` (in `machine.status.state.ts`) makes the controller saga send the line as-is, without adding it to the console command history; it is only handled while connected, so a line requested while disconnected is dropped, and `submitGrblMachineLine` also drops it during a job run (see [[running-jobs]]).
- **Pointer power.** `getPointerOnCommands(percent, sValueMax)` gives `M3 S<n>` and `G1 F100`, with `n = round(sValueMax * percent / 100)` and at least 1. The percent is clamped to 0.1..5 by `getClampedPointerPowerPercent`, the one owner of the pointer range, used by the builder and by the slice; so the pointer can never fire above 5 % of S max. `getPointerSValueMax(laserSettings, activeProfile)` picks that S max: the `$30` the connected laser reports validly (through `getValidlyReportedProfileValues`), else the active profile's `sValueMax`, else `DEFAULT_MACHINE_S_VALUE_MAX`. The laser's own `$30` wins, so a profile S max above the laser's (a 1000 profile on a `$30=255` laser) cannot lift the pointer past 5 % of `$30`.
- **Slice `laserPointer`.** State `isFiring` and `powerPercent` (default 1). Actions: `LaserPointerPowerChanged {percent}` (clamped), `LaserPointerFireRequested`, `LaserPointerReleaseRequested` (both from the UI), `LaserPointerFiringStarted`, `LaserPointerFiringStopped` (both from the saga only). Selectors: `selectIsLaserPointerFiring`, `selectLaserPointerPowerPercent` (the session's power). The power in use is `selectPointerPowerPercent` (`pointer.power.selector.ts`): the active profile's `pointerPowerPercent`, else the session's, clamped. `watchPointerPowerChanges` saves each `LaserPointerPowerChanged` into the active profile through `MachineProfileSaved`, so every laser keeps its own pointer power; the profile form edits it as well (`pointerPowerPercent` in `MACHINE_NUMBER_FIELDS`, with min, max and step, and a draft that starts from the session's power when the profile has none).
- **Saga `watchLaserPointer` (pointer safety).** On a fire request, only when connected and the last status is `Idle`, it puts `MachineLineRequested` for each pointer-on line for `selectPointerPowerPercent`, scaled by `getPointerSValueMax` over the connected laser's settings (`selectGrblSettings`) and the active profile, then `LaserPointerFiringStarted`. It then races every cut-off and stops on the first: release; window `blur`; document `visibilitychange` to `hidden` (one event channel, closed afterwards); `ConnectionStatusChanged` to anything but connected (disconnect or connection lost); `MachineStopRequested`; a `MachineStatusReceived` in `Alarm`; and the 10 000 ms maximum hold (`MAX_POINTER_HOLD_MS`). Stopping puts `M5` only when the connection status at that moment is still connected (a line could not be sent otherwise), then `LaserPointerFiringStopped`; the stop runs in a `finally`, so an error also turns the pointer off. Fire requests that arrive while firing are not taken and are ignored. Event names live in `browser.events.constants.ts`.
- **Position card.** `PositionCard` (in `MachinePanel`, between `MachineStatusCard` and `MoveCard`) renders `selectMachineStatus().workPosition` and `.machinePosition` as a table (rows Work and Laser with icons, columns X, Y, Z, `toFixed(3)`, missing values as `MISSING_VALUE_TEXT`). Read-only: no dispatch besides opening the connection popover from its `PlugBadge` while `selectIsConnected` is false, when it renders no table.
- **Status card.** `MachineStatusCard` (between `JobCard` and `PositionCard`, rendered only while `selectIsConnected`) is compact (`Panel isCompact`, as is `PositionCard`): `MachineStatusRow` (feed in mm/min and power as a percent of S max from `selectLaserChipPowerPercent`, each as icon plus short visible caption, then `MachineStateReadout`, the state badge) is its header action, and `MachineResetUnlock` sits beside it: Restart controller (`PoweroffOutlined`, text button, `aria-label` "Restart controller", tooltip and `aria-description` saying it stops all motion and resets GRBL with a soft reset, Ctrl-X; dispatches `MachineResetRequested`) and, only while connected and in Alarm, Unlock (`type="primary"`, its word, a warning `TooltipNoteIcon` and `aria-description` with `MACHINE_CONTROL_ALARM_NOTE`; dispatches `MachineUnlockRequested`). No machine command changed.
- **Set zero.** Lives in the Position card's title row as an icon button (since round 47), with the same `canSetZero` gate and line.
- **Move card.** `MoveCard` (in `MachinePanel`) builds a line with the pure builders and dispatches `MachineLineRequested`; it never touches the controller. `getMoveAvailability({ isConnected, machineState, hasHomingSwitches, isPointerFiring, isJobRunActive })` (`MoveAvailabilityConditions`) gates the controls: jog and go-to-zero need connected and `Idle` or `Jog`, Home needs homing switches and `Idle` or `Alarm`, Set zero needs `Idle`; all of them are locked while the pointer fires (`selectIsLaserPointerFiring`), since a move with `M3` active would drag the beam along its path (a second finger could reach the pad during a hold), and during a job run (`selectIsJobRunActive`), since a move would be mixed into the job. The 3 x 3 pad (`JOG_PAD_CELLS`: eight arrow buttons around an Origin centre that sends the go-to-work-zero line), an antd `Segmented` for the step (default 10 mm, kept in component state) and `JogSpeedInput` (an antd `InputNumber`, kept as a draft (`useNumberFieldDraft`; an empty draft stays empty while typing) and saved on blur or Enter through `MachineProfileSaved` with the feed rate held in 100–10000 by `getCommittedNumber`, an empty draft restoring the saved one; the handles keep their room and only fade in, so nothing moves on hover; disabled without an active profile). Home runs `$H` and is rendered only when the active profile has homing switches; Set zero sends `G10 L20 P1 X0 Y0`, an EEPROM offset that Stop and reset keep. Set zero and Home (with aim and home icons) share a row with `JogSpeedInput`. Unlock and Restart controller sit in the Status card.
- **Bed double-click move.** Off by default (`appPreferences.isBedDoubleClickMovingLaser`, `selectIsBedDoubleClickMovingLaser`, actions `BedDoubleClickMovePreferenceLoaded` / `BedDoubleClickMovePreferenceChanged`, stored by `watchAppPreferences` through `BED_DOUBLE_CLICK_MOVE_PREFERENCE_REPOSITORY` in `appState` key `bedDoubleClickMovesLaser`), switched in the STOP gear popover (`StopSettingsButton`). `BedObjects` puts `onDoubleClick` on its whole layer, so a double-click on an object moves the laser to that point too (the first click still selects the object; objects have no other double-click action, such as text editing); a double-click on a resize or rotate handle (`BED_HANDLE_SELECTOR`, `[data-handle]`) is ignored. `useBedDoubleClickMove` reads the store at the click and calls `getBedDoubleClickJogCommand`, which returns `undefined` unless the preference is on, `getMoveAvailability().canJog` holds and the state is exactly `Idle` (so no job, frame, homing, jog, alarm or hold) and no overlay is open (`selectIsAnyOverlayOpen`); otherwise it gives `getAbsoluteJogCommand` (`$J=G90 G21 X.. Y.. F..`, no Z, no `M3`/`S`) to `getClampedWorkPositionFromBedPoint` (the bed's own origin mapping, held inside the work area of `selectToolpathMachineArea`) at the profile jog speed. The line goes out as `MachineLineRequested`, so STOP and Escape cancel it like any jog. Blocked double-clicks do nothing and show no toast.
- **Laser pointer row.** `LaserPointerRow` is the last row of the Job card ([[running-jobs]]), folded or not, in the wide and narrow layouts; there is no separate pointer card. It is one row in every state (a `role="group"` named "Laser pointer"; while not connected the row is muted and compact: the slider is off, there is no button fill and the fire button shows its icon only; the details popover opens below the row and flips, so it never covers the readiness stepper): `PointerFireButton`, the power `Slider` (0.1..5 %, step `POINTER_POWER_STEP_PERCENT`, value from `selectPointerPowerPercent`, dispatching `LaserPointerPowerChanged`) with its figure (`MACHINE_LASER_POWER_PERCENT`), and `PointerDetailsButton`, a click `Popover` with the approximate watts of the active profile (`getPointerApproximateWatts`), the full `MACHINE_LASER_FIRMWARE_NOTE` and, only for a profile with air assist, an antd `Switch` that puts `MachineAirAssistChanged {isAirAssistOn}` and sends `M8` / `M9`. The switch reads `selectIsAirAssistOn` from the `machineStatus` slice, which starts as off and turns off again on `MachineStopRequested` and `MachineResetRequested` (both end in a soft reset, which switches the coolant off) and when the connection ends or is lost (the laser's air state is unknown afterwards).
- **Fire button.** `PointerFireButton` is enabled by `getCanFireLaserPointer(isConnected, machineState, isJobRunActive)` (connected, `Idle` and no job running, shared with the saga's own check), and stays enabled while the pointer fires even if the state leaves `Idle`, because a disabled button may never receive the `pointerup` / `pointerleave` that release it. It requests fire on a primary-button `pointerdown` (not on other buttons) and on a non-repeating Space or Enter `keydown`, and requests release on `pointerup`, `pointerleave`, `pointercancel`, `blur`, the key `keyup` and on unmount. Release is idempotent, so the extra triggers are harmless; the saga holds the cut-offs that do not depend on the UI.
- **Machine profiles dialog.** `TopBar` opens `MachineProfilesDialog` (an `AppModal`, 56 rem wide at most, so its fields are never cut off) with its "Machine profiles" button. `MachineProfilesEditor` keeps the edited profile in state (the active one, else the first, else a new one): `ProfileList` (antd `Menu` with an Active tag, New profile, Set active, Delete with a `Popconfirm`), `ProfileFileActions` (Import reads a file through a hidden file input and merges it with `getImportedProfilesDocument`, an invalid file shows `TOAST_PROFILE_IMPORT_INVALID`; Export downloads `getProfilesExportText`; GRBL settings is one dashed muted note with a clock icon, a tooltip and a small `SoonTag` in a "Coming soon" region, not a button or a form) and `ProfileForm` (one field per profile value, errors from `getMachineProfileErrors`, Save, and "Read from laser" through `LaserReadingAlerts`, which lists the values the laser reported, warns when none were and shows `MACHINE_PROFILES_LASER_MODE_OFF` when `$32` is reported off; reading fills the form only and Save keeps it).
- **Connection pill.** `ConnectionPill` shows the active profile's name.
- **Hardware.** The pointer sends `M3 S<n>` and then `G1 F100` (feed only, no axis word, so no motion; `POINTER_ON_COMMAND_PREFIX`, `POINTER_FEED_RATE`). Stock GRBL keeps `M3` lit whether or not the machine moves, so the pointer should light on stock GRBL; vendor builds like the ACMER's may differ. Not checked on hardware. Known follow-up: the ACMER hardware check (jog, go to zero, Set zero kept after Stop, Home and air assist if fitted, the pointer at 1 % and each cut-off, and whether a stationary pointer lights on its firmware, expected on stock GRBL) was deferred on 2026-10-31 because the laser was not available; the results update this article, the howto (`docs/howto/machine-control.md`) and LG-CTRL-18. The card's firmware note `MACHINE_LASER_FIRMWARE_NOTE` says "Some firmwares keep the laser off while the head stands still" and lists the cut-offs, with the hold limit interpolated as `MAX_POINTER_HOLD_MS / MILLISECONDS_PER_SECOND` seconds. The laser-mode warnings (`TOAST_LASER_MODE_OFF`, and `MACHINE_PROFILES_LASER_MODE_OFF` in the dialog) speak only about burn spots, never about the pointer.
- **Tests.** Saga tests run `newStore` against a `SimulatedLaserTransport` over a shared `GrblSimulator` whose settings are changed before connecting, with fake timers. The pointer saga tests read the requested lines by spying on `Action.prototype.toPlainObject`, which every class action (saga puts included) passes through on its way into the store. `vitest.setup.ts` clears the jsdom `localStorage` after every test.
