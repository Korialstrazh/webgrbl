# Layers and G-code

Layers come from colour: each distinct colour drawn by the project's SVG objects becomes a layer with laser settings, and the settings of a new layer come from the laser palette. This article covers the palette, the paint and layer derivation, and the layers in the project document, the layers UI with the palette dialog, and the toolpath model with its line mode and fill rasteriser, the G-code writer, the toolpath worker and the G-code export, the motion timeline with the time estimate, and the Toolpath view with its simulation (roadmap item 4a, done; 4b adds the 3D burn preview). User guide: `docs/howto/layers-and-gcode.md`. Design: `docs/superpowers/specs/2026-11-01_(02)_layers-gcode.spec.md`.

## Key Takeaways

- **Palette.** `Palette {version, entries}` holds `PaletteEntry {id, name, colour, mode, maxPowerPercent, minPowerPercent, speedMmPerMin, passes, airAssist, lineIntervalMm}`. `LAYER_MODE` is `line` or `fill`. `DEFAULT_PALETTE` is Cut (`#ff0000`, line, 100 %, 300 mm/min, 3 passes), Score (`#0000ff`, line, 30 %, 1500), Fill (`#00a000`, fill, 50 %, 2000) and the built-in Shading entry (`SHADING_ENTRY_ID`, `#000000`, fill, 60 %, 2000). Line interval defaults to 0.1 mm. Entries are validated by `getPaletteEntryErrors`, the palette is stored in localStorage (`palette.storage.ts`), and `getInkscapePaletteText` writes the `.gpl` file for Inkscape. `getNormalizedColour` turns names, short hex and `rgb()` into lowercase `#rrggbb`; `getParsedColour` also reads `transparent`, `rgba()`, `hsl()`, `hsla()`, percent `rgb()` and hex with alpha and returns `{colour, alpha}`.
- **Style resolver.** `getResolvedSvgStyles(svgDocument)` returns a `Map<Element, SvgResolvedStyle>` for every element (also inside `defs`, so the geometry code can reuse it for `use`). Precedence, lowest to highest: presentation attribute, `<style>` rule, inline `style`. Rules are simple selectors only (type, `.class`, `#id`, compounds of those, comma lists); weight is id > class > type, and a later rule wins at equal weight. Any other selector and every at-rule is ignored. `!important` is stripped, not honoured.
- **Inheritance.** `fill`, `stroke`, `stroke-width`, `fill-opacity`, `stroke-opacity`, `fill-rule` (`SVG_FILL_RULE`, default `nonzero`) and `visibility` fall back to the parent. `opacity` does not inherit but multiplies down the tree (`opacity` on the resolved style is the product along the ancestors). `display: none` hides the whole subtree (`isDisplayed`); `visibility: hidden` hides one element and a child can set `visible` again (`isVisible`). Defaults: fill black, stroke none, stroke width 1 (absolute units convert to user units at 96 px per inch). A fill or stroke that cannot be read, and `transparent`, is no paint (never inherited); the alpha of `rgba()` and friends is kept apart (`fillAlpha`, `strokeAlpha`) and folded into the paint opacity. `currentColor` uses the inherited `color` property (default black), also for `stop-color`. `url(#missing) #ff0000` uses its fallback colour. `stop-color` and `stop-opacity` are resolved too (not inherited), so classed gradient stops work.
- **Paints.** `getSvgPaints(svgText)` returns the distinct `SvgPaint {colour, opacity, gradient}` of the drawn elements (`path`, `rect`, `circle`, `ellipse`, `line`, `polyline`, `polygon`). It skips `none`, opacity 0, hidden elements, a stroke of width 0, the fill of a `line`, and elements inside `defs`, `clipPath`, `mask`, `pattern`, `marker` and `symbol`. `use` is not followed here. Opacity is element opacity times fill or stroke opacity, rounded to 3 decimals. Paints are distinct by colour, opacity and gradient.
- **Gradients.** `fill="url(#id)"` resolves to a `linearGradient` or `radialGradient` (`SvgGreyGradient`: stops with offset, colour and opacity, geometry, units). Stops and geometry follow `href` / `xlink:href` inheritance (cycle-safe, at most 16 links). The paint colour is the first stop's colour. A missing reference or a gradient without stops gives no paint.
- **Bed drawables.** `getBedDrawables(document)` (needs `DOMParser`, so it runs on the main thread) gives `BedDrawable`s in bed mm (front-left origin, Y up) in a project-wide paint order, plus `ObjectWarning`s for text, images and similar content. Curves are flattened to 0.05 mm on the bed. `SvgDrawablePaint` carries `fill`, `stroke`, `strokeWidth` (in the outline units), `fillRule`, and `fillGradientMatrix` / `strokeGradientMatrix`: the exact map from gradient coordinates to the outline units, built by `getSvgGradientMatrix` from the element matrix, the element's own user-space box for `objectBoundingBox` units, and `gradientTransform` (taken along the `href` chain by `getSvgGradientChain`); `getBedDrawables` composes it with the object matrix.
- **Toolpath model.** `getToolpath({drawables, warnings, layers, machineArea}, onProgress?)` is pure (no DOM), for the Web Worker. `machineArea` is a `ToolpathMachineArea {workAreaXMm, workAreaYMm, originCorner}` from `selectToolpathMachineArea` (the bed size the user sees plus the active profile's origin corner). `Toolpath {startPoint, moves, layers, warnings, bounds}`; `ToolpathMove {kind, from, to, powerPercent, feedMmPerMin, layerKey, airAssist}` with `TOOLPATH_MOVE_KIND` `travel` or `burn`; moves are chained from `startPoint`, the origin corner mapped into the bed frame (`getOriginMappedPoint(TOOLPATH_START_POINT, ...)`; (0, 0) for front-left, (workAreaX, 0) for front-right), so the first travel, its time and nearest-neighbour ordering start where the head really is; zero-length moves are dropped. `layers` is one `ToolpathLayerRange {layerKey, firstMoveIndex, lastMoveIndex}` per enabled layer with moves, all passes included. `bounds` is the box of every move end, so it covers burns and overscan but not the origin. Only enabled layers are used, sorted by `order`; each pass repeats the whole layer. It is the one model the G-code writer, time estimate and preview read.
- **Line mode.** `getLinePolylines`: a shape whose stroke is on the layer burns all its subpaths (open ones too); a shape whose fill is on the layer with a power above 0 burns its closed outline whatever its stroke (a white fill in the shading layer does not close an open stroke); both on the layer burn once at the higher power. Power is the layer maximum, or in the shading layer `min + (max - min) * (1 - L)` with L composited over white with the opacity (white burns nothing). `getPolylinesInBurnOrder` orders once per layer: by containment depth (open or closed outlines inside closed outlines of the layer, by box and first point), deepest first, then nearest-neighbour, picking candidates by box distance before scanning points; closed outlines start at their nearest corner, open ones at their nearer end. Every pass repeats that order.
- **Fill mode.** `getToolpathPaintAreas` turns drawables into paint areas back to front: every fill covers, whatever its layer; a stroke whose layer is in fill mode is outlined at its width (`getStrokeOutlineSubpaths`: one box per segment plus round-join wedges, all clockwise, nonzero) and covers; line-mode strokes never cover. Edges are sorted into horizontal bands (`getPaintAreaEdgeIndex`). `getScanlineRuns(paintAreas, y)` gives the visible runs with nonzero or evenodd parity per area and the topmost paint winning (`ScanlineCoverage`); white covers but burns nothing. `getFillLines` scans the layer box bottom to top at `lineIntervalMm` (10 mm at 0.1 mm gives 101 lines) and keeps lines that burn; `getRunFillSegments` gives colour layers the layer maximum and the shading layer the grey power, or for a gradient the power sampled along x through the inverse gradient matrix, stepped at 1 % (`SHADING_POWER_QUANTUM_PERCENT`). `getFillMoves` alternates direction, adds 2 mm overscan on each side as `burn` moves at power 0 and the layer feed, shortened to stay inside `[0, workAreaXMm]` (a burn edge already outside the area keeps no overscan on that side), so a fill at the bed edge never drives the head into a soft limit or the frame, crosses gaps up to 5 mm the same way, and travels over longer gaps. A realistic 20-object 200 x 200 mm fill takes about 1.5 s in node.
- **G-code writer.** `getGcodeText(toolpath, context)` writes GRBL 1.1 laser G-code: two header comments (`; webgrbl <version> - <project> - <ISO time>`, `; profile: <name>, S max <s>, origin <corner>`; every text field goes through `getGcodeCommentText`, which turns line breaks and control characters into spaces, `(` `)` `;` into `[` `]` `,`, and folds everything else to printable ASCII, because GRBL reads bytes 0x80-0xFF as realtime override commands even inside a comment), `G21 G90`, `M4 S0`, then `G0 X Y` for travel and `G1 X Y S F` for burns with `S` and `F` written only when they change; `M8`/`M9` around air-assist moves only when the profile has air assist; it ends with `M9` (if used) and `M5 S0`. `S = round(sMax * percent / 100)`, never above `sMax`; coordinates go through `getOriginMappedPoint` for the profile's origin corner. Only enabled layers are in the toolpath, so an all-off project writes no `G1`.
- **Toolpath worker.** Generation runs in a Web Worker so a large fill never freezes the app. `getBedDrawables` needs `DOMParser`, so the saga runs it on the main thread and sends only plain data: `ToolpathWorkerRequest {requestId, drawables, warnings, layers}` (not the document). `toolpath.worker.ts` is a thin adapter around `runToolpathWorkerRequest`, which calls `getToolpath(..., onProgress)` and posts `ToolpathWorkerMessage`s (`TOOLPATH_WORKER_MESSAGE_KIND` `progress` per enabled layer, `result`, or `error` with a developer-only text). `BrowserToolpathWorkerClient.generate(input, onProgress)` returns `{promise, cancel}`; it creates the worker lazily with `new Worker(new URL('./toolpath.worker.ts', import.meta.url), { type: 'module' })` (inline, as Vite needs), ignores answers with another request id, and `cancel` terminates the worker (the only reliable stop) so the next generation starts a new one. A worker `error` or `messageerror` rejects with `ToolpathWorkerError` and drops the worker. `dispose()` terminates the worker; the toolpath saga calls it in its `finally` when the store's sagas stop (the watchers are joined, so the `finally` runs only then). The client is injected like the GRBL dependencies: `newStore(grblDependencies, toolpathWorkerClient)`, and tests pass `FakeToolpathWorkerClient` (runs `getToolpath` at once, or holds generations to test cancels).
- **Toolpath state.** `toolpath` slice: `{status (TOOLPATH_STATUS idle | generating | ready | stale | failed), progress, toolpath, documentVersion, isGcodeExportConfirmationOpen}`. Every action in `PROJECT_DOCUMENT_CHANGE_ACTION_TYPES` (object and layer changes, undo, redo, load), and `ToolpathMachineAreaChanged`, bumps `documentVersion`, turns `ready` into `stale` and closes the export confirmation. `ToolpathReady {toolpath, documentVersion}` is dropped when the version is old. `ToolpathCancelled` returns to `idle`, or `stale` when an older toolpath is kept. The saga puts `ToolpathMachineAreaChanged` after a machine profile action only when `selectToolpathMachineArea` really changed (a jog-speed or name save keeps the toolpath current), and a running generation restarts on either kind of change. The RTK development checks skip `toolpath.toolpath`, which can hold millions of moves.
- **Toolpath saga.** `watchToolpath(client)`: the drawables come from a `BedDrawablesCache` (per object id, keyed by the SVG text and the placement fields `getObjectBedMatrix` reads, entries of removed objects dropped; paint orders are offset on assembly), so a layer-only change parses no SVG and moving one object parses only that object. `takeLatest([ToolpathRequested, ToolpathCancelled])` so a new request or a cancel stops the running generation, whose `finally` calls `cancel()`; progress comes back through a sliding channel as `ToolpathProgress`; a failure is logged, sets `failed` and shows a fixed toast. A document change while generating puts a new `ToolpathRequested`, debounced by `TOOLPATH_RESTART_DEBOUNCE_MS` (150 ms) so a held arrow key restarts once; a result for an older version is dropped meanwhile.
- **G-code export.** "Export G-code" in the Project menu and the Job card dispatch `GcodeExportRequested {isWarningConfirmed: false}`; both are enabled only with an active machine profile, at least one enabled layer (`selectEnabledProjectLayers`) and no running generation (`useGcodeExportAvailability`, with a tooltip saying a profile or a layer is needed). The saga stops without a profile, waits for a ready toolpath (requesting one when needed; a `ProjectDocumentLoaded`, or a `ProjectOpened` for another project id, drops the export with the info toast `TOAST_GCODE_EXPORT_DROPPED`, so the file is never another project's), and when the toolpath has warnings and they are not confirmed puts `GcodeExportConfirmationRequested` instead of downloading. `GcodeExportConfirmDialog` (a `BedRegionModal` mounted once in `AppRoute`, so STOP stays usable) lists each object with its warning texts; "Export anyway" dispatches `GcodeExportRequested {isWarningConfirmed: true}`, Cancel dispatches `GcodeExportConfirmationClosed` and downloads nothing. The download is `getGcodeFileName(project)` (`<safe name>.gcode`, sharing `getProjectFileBaseName` with the project file) as `text/plain`, with `getGcodeExportContext`: the profile's name, origin, work area and air assist, `sValueMax = getValidGcodeSValueMax(getPointerSValueMax(settings, profile))` (finite and at least 1, else 1000) and `APP_VERSION` (`__APP_VERSION__`, defined in `vite.config.ts` from `package.json`).
- **Job card.** `MachinePanel/JobCard` shows the enabled layer count ("2 layers · 1 off"), the time estimate (`getJobEstimateText`, a dash unless the toolpath is `ready`) and Export G-code as the full-width primary action; Start job and Frame job stay coming soon below it.
- **Design view by layer.** `BedObjectGraphic` draws an object through `ObjectDesignArtwork`: `getObjectDesignDrawing` (`src/utils/bed/`, cached per artwork) reads the SVG into the toolpath's flattened shapes in artwork millimetres, each fill and stroke paint with its layer key (`getPaintLayerKey`), grouped by `getDesignPaintRuns` into runs of one role and layer in drawing order. Each run is one `<g>` with a class and a `stroke` attribute from `getDesignLayerLooks`: Line runs draw as 1.5 px non-scaling outlines in the layer colour with no fill (CSS outranks the paths' own paint), off runs at 0.3 opacity, fill runs as drawn. An artwork whose paints all sit on enabled fill layers keeps the `<image>` (`isDesignDrawnAsAuthored`); otherwise a transparent hit rectangle over the box keeps selection and dragging working inside outlines.
- **Motion limits and timeline.** `getMachineMotionLimits(settings)` reads `$110`, `$111` (max rates), `$120`, `$121` (accelerations) and `$11` (junction deviation) from the connected laser's settings; a missing or non-positive value takes the GRBL default (`DEFAULT_MAX_RATE_MM_PER_MIN` 6000, `DEFAULT_ACCELERATION_MM_PER_S2` 1000, `DEFAULT_JUNCTION_DEVIATION_MM` 0.01), so the estimate also works offline. `getMotionTimeline(toolpath, limits)` plans like the GRBL planner: each move's cruise speed is its feed (or the axis-limited rate for travel) capped by the rate of the axes it uses, `getJunctionSpeed` limits each corner with the junction-deviation formula, `getPlannedJunctionSpeeds` does a forward and a backward pass (start and end at rest), and `getMoveMotionProfile` builds the speed-up, cruise and slow-down (a triangle when the move is too short to reach the cruise speed). It returns `{moveStartTimesS, moveProfiles, totalTimeS}`; zero-length moves take no time, and every burn including overscan and all passes counts. The timeline is selected on the main thread, once per toolpath and settings (`selectToolpathMotionTimeline`); `selectReadyToolpathTotalTimeS` is the total only while the status is `ready`, so a stale toolpath never shows as the current job. `selectIsSimulationPlayable` is true when that total is above 0.
- **Toolpath view.** The bed toolbar's Design / Toolpath / 3D `Segmented` is live for Design and Toolpath (3D is a disabled "3D · soon" option). `useBedViewMode` requests a toolpath when the view opens and the status is `idle` or `stale`. In the Toolpath view `BedPanel` shows `ToolpathLayer` instead of `BedObjects` (no editing; the object tools are hidden), `ToolpathToolbar` in the bed header (colour mode and "Show travel moves"; the group wraps to a row of its own on a narrow bed), the job size ("Job W x H mm", `getJobSizeText`) in the playback bar while ready, `ToolpathStatusOverlay`, `ToolpathWarningsPanel` (in the toolbar row, beside `ToolpathToolbar`) and `SimulationPlaybackBar`. The overlay shows a progress bar with Cancel while `generating`, and a banner with Generate (`idle`, also after a cancel), Regenerate (`stale`) or Regenerate with a failure text (`failed`). The warnings chip sits in the toolbar row, not over the bed, so it never covers the origin corner. A warning is about a part of an object (its text, its images, clipped parts), and the object's paths still burn, so the closed chip names the part and what happens to it per kind with a count (`getToolpathWarningsSummaryText`, `OBJECT_WARNING_KIND_LABEL_KEY`: "Warnings: text left out (1)", "clipped parts burn in full (1)"); open, its list drops below the chip with `getGcodeWarningLines` of a ready toolpath (the same lines as the export dialog). The bed keeps a minimum height of 12 rem. The live machine head and work-zero markers are not passed to `BedView` in this view: the layer draws its own head and the origin-corner marker (`getOriginMappedPoint` of (0, 0) for the profile), so two heads never show.
- **Toolpath drawing.** `ToolpathLayer` draws only a `ready` toolpath. `getToolpathDrawing(toolpath, displayMode)` groups the burning moves (burn kind, power above 0, so overscan is not drawn) into `ToolpathStrokePath`s, per layer in `by-layer` mode or per layer and power band in `power-shading` mode (`POWER_BAND_COUNT` 10 bands of 10 %), and prebuilds SVG path text in chunks of `TOOLPATH_PATH_CHUNK_MOVE_COUNT` (1000) moves; travel is one path. `getToolpathStrokePieces` cuts each group at the head: whole chunks before it are burnt (solid), whole chunks after it remain (dimmed, dashed) and only the chunk with the head is rebuilt, so a frame costs one chunk. A dash pattern could not be used because dashes restart at each `M`. Power shading draws more power more visibly on the dark bed; the shading layer is drawn in the muted text grey because its black would vanish. Colours of other layers are the layer colour itself.
- **Simulation.** `simulation` slice: `{currentTimeS, isPlaying, speed}` with `SimulationTimeSet`, `SimulationPlayToggled`, `SimulationPaused`, `SimulationSpeedSet` (`SIMULATION_SPEEDS` 1, 10, 50, 200 job seconds per real second) and `SimulationReset`. A new request, ready, failed result and every document change reset it to time 0 and paused. `watchSimulation` pauses a running playback after any action that leaves the toolpath unplayable (stale, generating, failed, gone, or 0 s). Every reader uses `selectClampedSimulationTimeS` (the stored time capped at the ready total), because a change of machine limits can shorten the job without resetting the time; dispatchers pass new times through `getClampedSimulationTimeS`. `getTimelinePosition(toolpath, timeline, timeS)` finds the move by binary search over the start times and the distance covered inside it (`getProfileDistance`) to give the head point, move index and power. `useSimulationPlayback` runs a `requestAnimationFrame` loop while playing (a frame counts at most `LONGEST_FRAME_REAL_S` 0.25 s real time) and pauses at the end and on unmount; `useSimulationTransport` holds the buttons: play at the end first rewinds, and Space on the focusable bar toggles play unless the target is a button or input. `SimulationLayerBar` (captioned "Burn time per layer", hidden with fewer than two layers, where one full-width segment would read as a second progress bar) shows each layer's share of the burn time (`getToolpathLayerBurnTimes`: burn moves with overscan, no travel), `SimulationReadout` shows X, Y and power, and the clock (`getSimulationClockText`) is rounded to the nearest second like the estimate.
- **Known limits.** Text that is not converted to paths, images (`ObjectWarning` kinds `text`, `image`), `<use>` beyond `SVG_USE_MAX_COPIED_ELEMENTS` (20 000 copied elements per SVG; uses inside `defs`, `symbol`, `clipPath` and `mask` are not expanded), content outside the page (`off-page`) and clip-path / mask content (`clipped`: burnt in full, no clipping in 4a) become `ObjectWarning`s in the toolpath; the toolpath shows the real result, the bed does not. The burn maps the root `viewBox` to the intrinsic box with `preserveAspectRatio="none"`, exactly like the bed image, so a file whose width / height ratio differs from its `viewBox` is stretched in both. Only line and fill modes exist (no raster, no `G2` / `G3`). The export does not check `$32`: the file uses `M4`, which needs laser mode on the controller. The palette dialog's folder hint lists Linux and Windows only; the macOS folder is in the howto.
- **Layers.** `ProjectLayer {colour, enabled, order, settings, paletteEntryId, isShading}`; `LayerSettings` is the palette entry without `id`, `name` and `colour`. `getLayerKey` is `SHADING_LAYER_COLOUR` (`'shading'`, not a colour) for the shading layer and the colour for any other.
- **Grey axis.** `isGreyColour` is true when the largest and smallest channel differ by at most 10 (`GREY_AXIS_TOLERANCE`); `getColourLightness` is `(r + g + b) / (3 * 255)`.
- **Derivation.** `getDerivedLayers(objectsPaints, palette, existingLayers)` keeps every existing layer unchanged and adds a layer for each key without one. `getPaintLayerKey`: greys and gradients with only grey stops go to the shading layer; a gradient with a colour stop goes to its first non-grey stop colour. A palette colour gets its entry's settings, enabled. Any other colour gets the settings of the nearest non-shading entry by Euclidean RGB distance (an unknown colour never borrows the shading settings), `enabled: false`, `paletteEntryId: undefined`. New layers are ordered palette colours before unknown colours, then fill before line, then palette order, and numbered after the existing layers' highest order.
- **Layers in the document.** `ProjectDocument.layers` holds every layer the project has had. Derivation runs in sagas before the put, never in the reducer: `deriveProjectLayers` (`project.layers.derive.saga.ts`) selects the palette and calls `getObjectsDerivedLayers`. The SVG import puts `ProjectObjectsAdded {objects, layers}` and the reducer adds only new keys (`getLayersWithNewLayers`), so the import and its layers are one undo step; `openLoadedProject` derives before `ProjectDocumentLoaded`. Undo and redo never derive again. `getObjectPaints` caches paints per SVG text (LRU of `OBJECT_PAINTS_CACHE_SIZE`, 200).
- **Visible layers.** `selectProjectLayers` (memoised with `createSelector`) keeps the layers whose key `getUsedLayerKeys` finds in the current objects, sorted by `order`. A layer whose colour is gone stays in the document, hidden, and undo brings it back with its settings.
- **Layer actions.** `LayerSettingsChanged {layerKey, settings}` (`getLayersWithSettings`: merged, ignored when a value is not finite, clamped by `getClampedLayerSettings` to the palette ranges, min power at most max power, whole passes), `LayerToggled {layerKey, enabled}` (`getLayersWithEnabledState`), `LayersReordered {layerKeys}` (`getLayersInOrder`: listed visible keys first, hidden layers after them in their old order, orders renumbered from 0). Each is one undo step; a helper gives the same array back for a no-op, so no step is made. All three are autosave change actions.
- **Storage and files.** The project row stores `layers` (no Dexie schema change); a row without it loads with `[]` and gets layers derived on open, and a malformed stored layer is dropped. Project files are version 2 with `layers`; version 1 files are read with layers derived from the palette passed to `getImportedProjectFile(text, palette)`; version 2 layers are type-checked (`isProjectLayer`, `isLayerSettings`), colour-normalised, de-duplicated by key and clamped, and layers matching no object are kept.
- **Layers UI.** `LayersSection` (in `DesignPanel`) lists `selectProjectLayers` in burn order: each `LayerRow` has a drag handle (HTML5 drag, with `onDragEnd` clearing a cancelled drag), an on/off checkbox, a button that opens `LayerSettingsDrawer`, and Move up/down buttons, shown on hover or focus and always in the tab order (always visible on a touch screen). The row shows the name on line 1 and a one-line summary on line 2, both cut short with an ellipsis and complete in the title. The row whose layer the drawer shows is highlighted as a whole (`isOpen`, accent border and edge; the open button has `aria-expanded`). The drawer is a `BedRegionDrawer` with `placement` left (`ANTD_DRAWER_PLACEMENT_LEFT`): it slides in from the bed region's left edge, which is the design panel's right edge, so it never covers the layer list and follows that edge when the panels are resized; its width is `min(23.75rem, 100%)`, its title is the layer name under a small "Layer settings" overline, its mask is clear (the bed stays visible; a click on it and Escape still close the drawer), so in a narrow window, where the bed region is below the design panel, it is never wider than the bed region. Reordering uses `getLayerKeysWithMovedLayer` and dispatches `LayersReordered`. A layer whose entry is gone shows "Not in the palette". The drawer's fields (`LayerSettingsFields`) dispatch `LayerSettingsChanged`; "Save to palette" dispatches `PaletteEntrySaved` (and `LayerPaletteEntryLinked` when the layer had no entry, so it stops saying "Not in the palette"); the line interval field shows for fill mode only, the air-assist switch only when the active profile has air assist, and the "Save as material preset" button is `ComingSoon`, and "Edit palette..." opens the palette dialog.
- **Palette dialog.** `PaletteDialog` is an `AppModal` (overlay id `palette-dialog`, so Escape closes it; 56 rem wide at most, the list and form stack below 48 rem; row text is cut with an ellipsis, never under the icon buttons) owned by `DesignPanel`; both the drawer's "Edit palette..." and the "Palette" button in the Layers header open it. `PaletteEditor` remembers the edited entry; `PaletteEntryList` shows the entries with the same drag and Move buttons (reusing `getLayerKeysWithMovedLayer`, dispatching `PaletteEntriesReordered`), a Delete button behind a `Popconfirm` (none for the shading entry, `PaletteEntryDeleted` also protects it) and "+ New colour". `PaletteEntryForm` edits a draft and dispatches `PaletteEntrySaved` only after `getPaletteEntryErrors(draft, otherEntries)` finds nothing: switching entries drops the draft, and a new entry exists only after Save. The colour uses an antd `ColorPicker` (hex, no alpha) stored through `getNormalizedColour`, locked for the shading entry. `getPaletteEntryErrors` takes an optional list of the other entries and reports `PALETTE_ERROR_COLOUR_DUPLICATE` for a colour another entry already uses, because layers are matched to entries by exact colour (the shading entry's black counts, so no other entry can use `#000000`). `PaletteFileActions` has "Reset to defaults" (behind a `Popconfirm`, `PaletteResetRequested`), "Export for Inkscape" (`PaletteExportRequested`) and the folder hint (`~/.config/inkscape/palettes/` on Linux, `%APPDATA%\inkscape\palettes\` on Windows, literal CSV strings).
